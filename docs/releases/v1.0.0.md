# boomPI v1.0.0 教学最终基线

- 发布日期：2026-08-04（Asia/Shanghai）
- 源码标签：`v1.0.0`
- 目标硬件：自研 RV1106 板、双麦克风、扬声器、ST7789P3 320×240 横屏、GT911 触摸、SC3336 摄像头
- 客户端：C++17 / CMake / Buildroot GCC 8.3 / uClibc
- 服务端：Go 1.26 / 单文件可执行程序 / `CGO_ENABLED=0`
- 云端区域：中国内地（北京）

## 1. 这次发布是什么

`v1.0.0` 是 boomPI 第一版可演示、可教学、可继续优化的稳定基线。它已经完成从板端唤醒、
双麦采集、AEC/VAD、局域网 WSS、Qwen ASR/对话/TTS，到扬声器流式播放、播放中同句打断、
三秒追问、LVGL 屏幕和触摸控制的完整闭环。

本版冻结的是功能与交互基线，不把尚未量化的声学上限冒充完成项。用户已经在真板上完成
最终人工验收，确认问答、连续播放、无明显自激、打断后提交新问题、屏幕触摸和实时音量滑块
均可用。后续版本从本标签开始，只做带前后证据的性能、声学和体验上限优化。

## 2. 产品目标与部署形态

boomPI 不是把所有云能力塞进板端。它把实时硬件和交互留在 RV1106，把 API Key、模型接入和
会话编排放到同一局域网内的个人电脑：

```text
双麦 / 扬声器 / 触摸屏 / 摄像头
                 │
        RV1106 boompi-client
       C++17，实时音频与 LVGL
                 │
       UDP 发现 + 持久 WSS/TLS
                 │
          boompi-server
       Go，单文件、无数据库、无容器
                 │
      Qwen 中国内地（北京）API
```

这样做有三个直接好处：板端不保存 Qwen Key；服务端更换模型不需要重烧 BSP；学生拿到服务端
可执行文件后只需配置 Key，就能在可信局域网内启动完整演示。

## 3. 仓库结构与职责

```text
client/

  src/application/              唯一会话 actor 和状态机
  src/audio/                    音频门面、播放线程、有界 TTS 环
  src/network/                  WSS/TLS、协议收发、网络启动与发现
  src/platform/rv1106/          ALSA、重采样、Rockchip 3A、Snowboy、VAD
  src/ui/                       LVGL、ST7789P3、GT911、摄像头预览
server/
  cmd/boompi-server/            单文件服务端入口
  internal/app/                 设备会话、上下行节拍、取消编排
  internal/backend/             可替换的对话后端契约
  internal/backend/qwen/        Omni Realtime 直连模式
  internal/backend/qwenpipeline/ ASR → LLM → 流式 TTS 组合模式
  internal/session/             有界 session actor
  internal/transport/           WSS/TLS 与单 writer
  internal/discovery/           UDP 局域网发现
  internal/identity/            本地 TLS 身份与 SPKI
protocol/                       客户端/服务端共同的 v1 wire contract

```

没有再引入另一套 `App/Driver/Inf`、通用 worker、插件工厂或企业级 supervisor。每个目录只有一项
清晰职责，教学时可以沿着“采集一帧 → 状态机 → 网络 → 服务端 → 播放一帧”顺序阅读。

## 4. 板端客户端架构

### 4.1 线程与所有权

正常语音和显示在线时，客户端有 6 个自有长期执行上下文；打开摄像头页面时增加到 7 个。

| 执行上下文 | 调度 | 唯一职责 |
| --- | --- | --- |
| application actor | 普通调度 | 唯一修改会话状态、turn、epoch、超时和重连状态 |
| capture/DSP | 申请 `SCHED_FIFO 40` | 独占 ALSA capture、3A、Snowboy、VAD，生产 4 帧固定队列 |
| playback | 申请 `SCHED_FIFO 30` | 独占 TTS 环、24→48 kHz、gain/limiter 和 ALSA playback |
| WebSocket service | 普通调度 | TLS/WSS I/O，回调只投递 64 项固定事件环 |
| NetworkBootstrap | 普通调度 | 以太网/Wi-Fi、DHCP、UDP 发现、endpoint 持久化 |
| UI | `nice +5` | 30 FPS 合并刷新、SPI 写屏、GT911 触摸，不处理 PCM |
| camera（按需） | 普通调度 | 仅在摄像头页面采集和转换预览帧，离开页面即回收 |

业务状态只由 application actor 写。音频线程不切换 turn，网络回调不直接执行状态机，UI 拖动
也不进入音频队列。实时 PCM 使用对象内固定数组和有界环，避免逐帧 heap 分配和无界排队。

### 4.2 上行音频数据流

```text
ALSA capture
48 kHz / S16_LE / Mode1 / 4 ch / 20 ms
  [mic0, mic1, refL, refR]
        │
        ├─ 保持四通道相位，48 → 16 kHz
        ├─ AEC 输入只选 [mic0, mic1, refL]
        ├─ 丢弃与 refL 高度重复的 refR
        └─ Rockchip 3A → 16 kHz mono
                    │
                    ├─ Snowboy 唤醒词
                    ├─ WebRTC VAD
                    └─ WSS 16 kHz / mono / 20 ms PCM
```

ALSA 实际协商：capture period/buffer 为 `960/1920` frames；playback 为 `960/3840` frames。
采集线程持续排空硬件，即使云端等待或网络重连也不暂停。application 如果落后超过
`4 × 20 ms`，队列会丢弃陈旧帧并显式产生 `discontinuity`，不会静默拼接错误时间轴。

Rockchip 3A 固定调用为 `init(16000,16,2,1)`，即双麦、单硬件参考。当前 mask `1109`
启用 FastAEC、AES、ANR、Dereverberation 和 STDT，vendor AGC 关闭。Codec Mode1 直接回采
真实播放到 `refL/refR`，项目不维护软件 reference ring，也不把尚未播放的 TTS 数据当参考。

### 4.3 下行音频数据流

```text
WSS 24 kHz / S16_LE / mono / 20 ms
        │
        ├─ 初始抖动缓冲 180 ms（短回复 EOS 可提前）
        ├─ 固定 75 帧 / 1.5 s 硬上限
        ├─ 24 → 48 kHz
        ├─ 原子软件音量 + limiter
        └─ 复制为双声道 → ALSA playback
```

服务端按 20 ms 对下行 PCM 做节拍控制。v1.0.0 额外修复了桌面定时器迟到后的追赶突发：
下一帧至少保留 15 ms 间隔，正常仍以 20 ms 媒体时钟推进，完整一帧的停顿则重新定基准。
这避免 Windows/macOS 调度抖动产生 5–10 ms 连发，再把瞬时突发传给板端 jitter queue。

### 4.4 唤醒、VAD、追问和打断

主状态机为：

```text
WAITING_FOR_WAKE
  → WAITING_FOR_SPEECH
  → CAPTURING_SPEECH
  → WAITING_FOR_RESPONSE
  → PLAYING_RESPONSE
  → DRAINING_PLAYBACK
  → WAITING_FOR_FOLLOW_UP
```

冻结参数：

- Snowboy sensitivity：`0.7`
- 普通 VAD 原始麦门：`-35 dBFS`
- 播放期打断门：`-25 dBFS`
- pre-roll：25 帧 / 500 ms
- 唤醒后首次开口：最多 6 s
- 语音结束：连续静音 700 ms
- 单轮最长录音：60 s
- 免唤醒追问：3 s

播放期不能只靠 raw mic 音量打断，因为扬声器本身会抬高麦克风电平。当前流程先由 3A 后 VAD
连续确认近讲候选，再短暂静音并等待硬件 reference 降低，清除声学尾音后进行二次确认。
确认成功才丢弃旧 TTS、发送 `response.cancel`，并把同一句话的 AEC 后 pre-roll 作为新 turn
开头提交；用户不需要再说第二遍。失败则恢复播放并进入冷却，避免自激反复切断回答。

### 4.5 LVGL 与本地应用

界面使用 LVGL 8.2 和 FreeType，固定 320×240 横屏。首页采用统一深色空间风格，当前入口包括
小智、摄像头、时间、天气、Wi-Fi 配网、资源监视和 YOLO 占位。YOLO 推理不属于本版闭环。

- 小智页：动态语音球、状态、两行中文字幕、点击唤醒/打断。
- 音量：0–100% 横向滑块，拖动只覆盖一个合并邮箱；application 读取最新值后原子更新播放
  gain，松手才写 `/userdata/boompi/config/ui.settings`，避免刷 flash 或挤占音频动作队列。
- 静音：保存上次非零音量，点击后真实置 0，再次点击恢复，不再只是图标效果。
- 亮度：当前背光只有 GPIO 开关证据，因此 UI 只承诺开/关，不伪造 PWM 多级亮度。
- Wi-Fi：显示二维码和配网步骤，配合 `boompi-provision` 临时 AP/网页完成 2.4 GHz 配网。
- 摄像头：进入页面后按需启动 `/dev/video14`，以 NV12 576×324/25 输入，经 FFmpeg 降为
  4 FPS、缩放为 320×180 RGB565 本地预览；退出即回收，不常驻抢占音频资源。

ST7789P3 SPI 配置为 80 MHz，UI 目标刷新率 30 FPS；音频线程优先级高于 UI。最终测试还修复了
滑块触摸与旧全屏亮度手势冲突，拖动音量不再误关背光。

## 5. Go 服务端架构

服务端是一个无数据库、无容器、无 CGO 的单文件程序。第一次启动会在当前目录生成
`config.yaml` 和稳定 TLS 身份；填写中国内地（北京）区 Qwen Key 后再次启动即可。

### 5.1 数据流

```text
设备 WSS reader
  → 严格校验 hello / token / IDs / sequence / epoch
  → session actor（有界队列、单一会话所有权）
  → ConversationBackend
       ├─ intelligence：实时 ASR（失败可降级 batch）
       │                 → 流式 LLM
       │                 → 连续 server_commit TTS
       └─ realtime：Qwen Omni Realtime 直连
  → 20 ms paced downlink
  → 单一 WSS writer
```

默认使用 `intelligence`，因为 ASR、对话模型和 TTS 可分别替换，教学上更直观。后端契约保持
可插拔，但没有动态插件系统。每个设备连接只有一个 session actor 和一个 WebSocket writer；
provider、actor、transport 均使用固定容量 channel。拥塞只取消当前 turn，不无限积压，也不把
健康的持久连接误判为断线。

### 5.2 默认 Qwen 配置

| 配置 | v1.0.0 默认值 |
| --- | --- |
| 区域 | `china-beijing` |
| conversation mode | `intelligence` |
| realtime/Omni model | `qwen3.5-omni-plus-realtime` |
| ASR | `qwen3-asr-flash` |
| 对话模型 | `qwen3.6-flash` |
| reasoning effort | `none` |
| TTS | `qwen3-tts-flash-realtime` |
| TTS voice | `Cherry` |
| search | `off` |
| 会话上限 | 20 turns / 24,000 context tokens |

服务端只保留当前对话上下文，不写数据库。播放被打断时，v1 协议没有可靠的文本/播放位置映射，
因此服务端删除整条被打断 assistant turn，避免把用户没有听到的完整回答留进下一轮上下文。

## 6. 网络、协议与安全边界

- UDP `17807`：局域网发现；客户端只信任响应来源 IP，不把 UDP 当身份认证。
- WSS `17806`：同一持久连接承载 JSON 控制帧和二进制 PCM。
- TLS：服务端首次生成稳定身份；客户端采用 TOFU 保存 SPKI，后续地址变化仍要求同一 SPKI。
- 设备认证：32–256 bytes 的共享教学令牌，在打开付费 provider 会话前验证。
- 心跳：服务端默认每 10 s Ping；连接超时 30 s。
- 协议身份：`device_id/session_id/turn_id/stream_id/epoch/sequence` 共同阻止迟到帧污染新 turn。
- PCM：固定 64-byte big-endian header，样本仍为 little-endian S16_LE；实时音频断线后不重传。
- JSON：客户端 cJSON 边界拒绝重复 key、错误类型、无效 UTF-8、负数/小数 ID 和越界长度。

API Key 只保存在服务端私有 `config.yaml` 或 `DASHSCOPE_API_KEY` 环境变量中。默认不持久化
原始录音、播放 reference 或完整对话，日志不输出 Key、令牌、Workspace ID 和证书私钥。

教学 token + TOFU 适合可信局域网，不等于企业级配对。设备唯一证书、正式配对、签名 OTA 和
A/B 系统更新属于后续产品化范围。

## 8. 配置、构建与运行

### 8.1 服务端三步启动

```powershell
# 1. 首次运行生成 config.yaml
.\boompi-server-windows-amd64.exe

# 2. 编辑 config.yaml，只填写中国内地（北京）区 Key
# qwen_api_key: "sk-..."

# 3. 再次启动
.\boompi-server-windows-amd64.exe
```

Linux/macOS 首次下载后先执行 `chmod +x boompi-server-*`。也可以使用
`DASHSCOPE_API_KEY`，它优先于 YAML。真实 Key、`config.yaml` 和 `state/` 都不能提交。

### 8.2 服务端源码构建

```text
cd server
go test ./...
go vet ./...
CGO_ENABLED=0 go build -trimpath ./cmd/boompi-server
```

### 8.3 RV1106 客户端交叉构建

先准备匹配 BSP 的工具链/sysroot，以及仓库外的 vendor、LVGL、OpenSSL、Boost 和 VAD 路径，
再使用唯一生产候选入口：

```text
cmake --preset rv1106-candidate
cmake --build --preset rv1106-candidate --parallel
```

产物必须通过 ELF32 ARM、EABI5、hard-float、uClibc、RPATH 和开发机路径检查。板端更新：

```powershell
scp boompi-client rv1106-board-3:/tmp/boompi-client
ssh rv1106-board-3 "/usr/sbin/boompi-clientctl update /tmp/boompi-client"
ssh rv1106-board-3 "/usr/sbin/boompi-clientctl start"
ssh rv1106-board-3 "/usr/sbin/boompi-clientctl log"
```

### 8.4 Wi-Fi 配网

```text
boompi-clientctl provision
```

板端显示二维码并创建 `boomPI-Setup` 临时热点。手机连接后打开 `http://192.168.4.1/`，提交
2.4 GHz Wi-Fi。正常运行时以太网优先，Wi-Fi 备用。

## 11. 明确边界

v1.0.0 不包含：YOLO 推理、多模态摄像头对话、长期记忆、工具调用、在线音乐、企业级配对、
设备证书体系、签名 OTA、A/B rootfs 和数据库。SC3336 当前只做本地屏幕预览。

以下是后续量化优化项，不影响本次功能发布：

- 最终外壳下的 ERLE、残余回声、远场、最大音量和受控 double-talk 曲线。
- 唤醒词误唤醒/漏唤醒率，以及自训练 NPU 唤醒模型替换 Snowboy 的收益。
- 端到端首音、打断确认和连续运行 8/24/72 小时数据。
- 断网、Wi-Fi 漫游、服务端换机和高丢包环境下的恢复体验。
- UI 动画、资源占用和 SPI 刷新上限；YOLO 最后接入。

最终发布审计时板端物理链路已经断开，因此没有伪造一次“当前在线”的 PID、`/proc` 实时策略或
最新 XRUN/core 统计；本节采用断线前最后一次部署哈希、日志和用户人工验收。长期稳定性仍需
后续单独留出受控窗口量化。

## 12. v1.0.0 之后的规则

1. `v1.0.0` 标签是不可变基线，不移动、不重打。
2. 新工作从 `main` 或 `v1.0.0` 建 `codex/*` 分支。
3. 每项优化先记录假设、测试条件和基线，再给出修改后的同条件数据。
4. 声学参数不得因一次主观试听直接定版；至少保留原配置和可回退证据。
5. 不牺牲当前已通过的连续播放、无明显自激和同句打断体验换取单项跑分。
6. 不增加无实测需求的抽象层、线程、动态插件或企业级防御代码。
7. 任何声称“优于 v1.0.0”的版本都必须重新通过 host、Go、严格交叉构建和真板人工闭环。
