# boomPI 教学文档协作规范

本文件适用于当前工作区中的课程文档、章节源稿、配图、构建脚本、审校报告和最终 DOCX。进入本目录工作的任何智能体，必须先读完本文件，再读取与所写章节直接相关的原始参考文档、硬件资料和当前状态台账。

用户最新的明确要求优先于本文件。除非用户明确改变方向，否则不得自行恢复已经被否定的写法。

## 1. 文档目标与读者

读者害怕技术名词，也难以跟随很长的逻辑链。文档应像一位真正做过板卡操作的老师在旁边带着学生完成项目，而不是技术白皮书、需求规格书、AI 摘要或讲师提纲。

合格正文具有这些特征：

- 先说明眼前为什么要做这一步，再给出操作或电路，再解释观察到的结果。
- 专业词第一次出现时，先用一句普通话说明用途，再给正式名称；不连续堆叠缩写。
- 一段只承担一个中心意思，段落长短允许自然变化，不追求机械对称。
- 过渡句必须来自真实因果，例如“系统能够从 eMMC 启动以后，还需要联网”，不能用空泛的“接下来我们继续学习”。
- 操作文字和真实截图相邻，读者能对照完成；抽象说明不能替代实际界面、终端或板卡现象。
- 不炫技，不提前展开暂时用不到的算法、协议和性能细节。音频实现统一放在整条学习路线的最后阶段。

## 2. 什么是“AI 味道重”

出现下列行为时，视为 AI 味道重，必须重写：

- 每章都套用“本章目标—准备—操作—你应该看到—失败怎么办—小结—通关卡”的同一模板。
- 频繁使用“可以把……理解成……”“不是……而是……”“首先、其次、最后”“值得注意的是”“这一步非常重要”等套话，却没有给出具体对象和结果。
- 用大量拟人、比喻或问答句解释本来一句话能说清的内容。
- 每两三段插一个小标题，标题只管一小段，导致读者不断切换话题。
- 大量使用“我们将”“后续会”“本节主要介绍”等自我描述，而不直接进入事实或操作。
- 把源码配置、历史记录、设计目标写成本轮实测；或者重复堆放“可能、通常、一般来说”来掩盖证据不足。
- 段落结构、句长、加粗方式和总结句高度一致，读起来像批量生成。
- 只列参数、术语和模块名，没有说明它们为什么在当前板卡上出现。
- 搜索了网络资料，却只在末尾列链接，没有把官方事实、截图和板上设计真正对应起来。
- 使用虚构终端、概念图或其他开发板照片冒充当前 boomPI 的真实操作证据。

“AI 味道轻”不是故意写得口语化，而是让文字带有真实教学动作：说明一个具体问题，展示实际动作或原理图，指出学生此刻应关注的位置，再自然进入下一步。参考文档中的节奏、截图密度和说明方式优先于通用写作模板。

## 4. 章节组织

- 一次只完成一章。前一章通过技术、可读性、视觉和排版检查后，才进入下一章。
- 每章建议保留 4～8 个主要分节；可连续叙述的内容不要继续拆标题。
- 正文可见标题不超过三级。只有一个自然段的标题应合并回相邻内容。
- 章节开头直接承接上一章留下的实际问题，不写空泛学习目标。
- 章节结尾只总结本章真正完成的闭环，并给出下一章的自然入口。
- 操作章节遵循“说明目的—执行动作—紧邻截图—说明结果—处理常见失败”的节奏，但不得把这五项机械地做成固定标题。
- 概念章节遵循“用途—官方定义—本板对应—为什么这样设计”的连续叙述。
- 原理图章节按模块组织；整页原理图只做导航，正文使用干净模块裁剪，不在原理图上画红框、箭头或编号。
- 芯片手册提出要求、板级电路实现要求时，手册原页截图和对应原理图模块必须相邻，正文明确说明两者的因果关系。
- 硬件逐项测试必须位于项目开发之前；音频功能位于最后，不提前成为开篇主线。

## 5. 内容证据与技术事实

正文结论必须来自以下来源之一，并在内部台账绑定：

1. 当前原理图和 `netlist.json`：只能证明设计连接。
2. 芯片、器件和软件的官方资料：只能证明厂商规格和要求。
3. 当前仓库源码、配置和构建日志：只能证明实现或构建状态。
4. 带时间、板卡、镜像和命令的当前板端证据：才能证明本轮实测。
5. 历史 HIL：必须写明历史条件，不能绑定到新的二进制或镜像。

禁止把外接屏幕、触摸、摄像头、麦克风或扬声器写成主板贴片器件。禁止把其他 RV1106 开发板的接口、照片、设备节点和命令套到 boomPI。

需要网络查询时，只使用官方文档、芯片/器件厂商资料、标准组织和项目官方仓库。网络资料必须在正文中发挥作用：给出支持当前解释的事实、页面或截图，并与本板设计或操作对应；不得只堆链接。

无法证明的内容写入章节审校记录，不用虚构文字填满正文。最终稿中的“待验证”必须极少且有明确原因，不能成为逃避实测的模板。

## 6. 图片与截图

- 烧录、登录、配置、编译、传输和板端测试以真实截图为主。每个关键动作至少保留动作前或动作后证据，关键闭环同时保留动作和结果。
- GUI 截图可以使用红框、箭头和编号指示点击位置，保持与参考文档一致；同一图不要同时放过多标注。
- 原理图使用干净裁剪，不画框。芯片手册允许直接截取原页的关键表格或时序图。
- 总览框图只保留模块和连接关系，不塞器件位号、长型号、来源声明或大段限制说明。
- 不使用由日志重新排版生成的“终端截图”冒充真实终端；如果只能使用摘录，图注必须如实写“证据终端摘录”。
- 图片独占段落、居中、保持比例，图注紧随图片。截图应裁掉无关窗口、个人路径、账号、密钥、Wi-Fi 密码和其他隐私。
- 图片不足时先建立截图任务清单，再继续不依赖该图片的正文；不得用概念图填补本应存在的真实操作图。

## 7. Word 与版式

- A4 纵向，上下边距 2.54 cm，左右边距约 3.18 cm。
- 正文中文宋体 10.5 pt，英文和数字 Times New Roman，1.5 倍行距，两字符首行缩进，两端对齐。
- 标题使用真正的 Word 标题样式和自动多级编号，不手工输入编号模拟结构。
- 图片使用行内对象；禁止浮动图片覆盖正文。图片、图注和相邻说明尽量同页。
- 代码和终端使用 Consolas 等宽字体，保证复制和换行可读，不用截图替代可复制代码。
- 不用连续回车制造空白，不出现孤立标题、孤立图注、半页空白或被压缩得无法阅读的整页原理图。
- 每次修改 DOCX 后必须渲染为 PDF/逐页 PNG，检查全部页面，而不是只检查文件结构。

## 8. 多智能体协作

角色固定为：

- 章节作者：唯一可以修改该章源稿和构建脚本的角色。
- 技术审校：只读检查事实、来源、命令、安全边界和证据绑定。
- 可读性审校：只读检查逻辑跳跃、AI 套话、标题碎片和初学者负担。
- 视觉审校：只读检查截图是否真实、清晰、隐私安全，并建立缺图清单。
- 主智能体：整合审校意见、决定最终改动、生成 DOCX、完成 Git 提交和推送。

同一时刻禁止多个智能体修改同一章。审校智能体只写入 `docs/course/audit/`，不得直接修改正文。所有智能体在开始工作前读取 `docs/course/status/chapters.md`，结束时报告修改文件、发现的问题和剩余阻塞。

## 9. 每章完成门禁

一章只有同时满足以下条件才算完成：

- 标题树连续，没有无意义的单段小标题。
- 开头、分节之间和结尾不存在突然换话题。
- AI 套话审查通过，正文没有批量模板感。
- 所有技术结论有来源，设计事实、源码状态和实测结果没有混写。
- 关键操作拥有真实截图；缺图项已明确记录且不被虚构素材代替。
- 代码、命令、路径和参数经过实际核对。
- DOCX 图片全部为行内对象，可访问性检查无高优先级问题。
- 最新 DOCX 已完成逐页视觉检查。
- 章节源稿、必要配图、审校记录和最终 DOCX 已进入 Git。

## 10. Git 工作流

课程文档的远程版本以 `boomPI` 仓库 `docs/course/` 为准。外层工作区的 `待编写的文档/逐章审阅/` 保存便于用户直接打开的同步副本。

- 使用 `codex/docs-course-rewrite-20260810` 分支。
- 禁止 force push、rebase 用户历史、reset --hard 或清理无关未跟踪文件。
- 每完成一章，只提交该章、状态台账和必要的共享规范。
- 提交信息格式：`docs(chXX): 完成<章节名称>`。
- 提交后立即执行 `git push origin codex/docs-course-rewrite-20260810`。
- 推送失败时保留本地提交，记录错误并继续不依赖远程的工作；不得反复修改认证配置或暴露凭据。
- 不提交临时渲染目录、缓存、私密截图、原始录音、密钥、真实 Wi-Fi 配置或无关构建产物。

## 11. 章节状态台账

`docs/course/status/chapters.md` 是唯一进度台账。每章记录：

- 状态：未开始、写作中、审校中、待截图、已完成。
- 章节作者和审校角色。
- 主要参考文档及页码。
- 技术证据和截图状态。
- 最新 DOCX 路径。
- Git commit 与远程推送结果。
- 仍未关闭的问题。

如果台账与口头说明冲突，以最新 Git 中的台账和用户最新反馈为准。
