# 第4章终端操作后移至第6章的技术与课程顺序评估

## 结论

**有条件推荐。** 把 `pwd`、`ls`、`ps` 的操作、真实输出和结果判读全部从第4章后移到第6章，技术上成立，也更符合当前课程主线：

`第3章解释操作系统职责 → 第4章解释Linux系统的组成与名词 → 第5章说明构建、镜像与烧录 → 第6章登录烧录后的板卡，先建立系统基线，再逐项测试硬件`。

这样可以直接消除第4章“正文要求学生操作、成品却没有真实终端证据”的矛盾；第4章恢复为概念章，第6章成为操作章，截图密度也与课程规范一致。

但必须同时关闭一个依赖冲突：当前状态台账把第5章命名为“Buildroot、固件烧录与HelloWorld”。若第5章要登录板端、传文件并运行HelloWorld，就已经依赖工作目录、文件路径和板端终端操作，不能等到第6章才第一次解释这些内容。两种处理方式只能选一种：

1. **推荐方案**：第5章保留主机侧构建、镜像校验、烧录与启动门禁；把HelloWorld的板端部署、运行和结果移到第6章的系统基线之后，作为“第一份可控程序”，然后再进入硬件资源。
2. **保守方案**：第5章保留运行HelloWorld所必需的最小登录、工作目录和文件执行动作；此时不能再宣称 `pwd`/`ls` 操作“全部后移”，第6章只能补充系统化解释与证据。

若不处理HelloWorld依赖，后移方案在课程顺序上是 **REJECTED**；采用推荐方案后为 **PASS**。

## 第4章应保留什么、删除什么

### 可以保留

- Linux内核与用户空间不是同一层：内核管理处理器、内存和驱动，Shell、命令、库、配置和应用位于用户空间。
- Ubuntu是开发电脑上的Linux发行版；Buildroot是主机侧构建工具；板端运行构建产物，不是在运行Buildroot工具本身。
- Linux把可访问的文件和接口组织在从 `/` 开始的一棵目录树里。
- `/etc`、`/bin`、`/sbin`、`/proc`、`/sys`、`/dev`的通用职责；明确 `/proc`、`/sys`、`/dev`不应被讲成eMMC中的普通静态文件夹。
- 程序运行后形成进程；PID用于区分一次运行。进程名出现在列表中只是一瞬间的系统线索，不是服务健康或功能通过。
- 设备节点是应用进入内核驱动的一类入口；节点存在不等于硬件已连接、驱动正确或功能通过。
- 当前上游5.10文档与厂商5.10.160之间的版本边界，以及Ubuntu主机和armv7l板端二进制架构差异。

### 应从第4章删除或改成纯概念

- 删除“登录后输入 `pwd`”“输入 `ls /`”“`ps`可以读取”等动作句。
- 删除“本轮原始记录中PID 1名为`init`”等结果句；该结论应与第6章的真实 `ps`/`/proc/1` 输出相邻。
- 不在第4章列出当前板的根目录实际清单、当前挂载、分区容量、进程表或具体 `/dev/videoN`、`/dev/input/eventN`。
- 不把概念目录树图写成当前镜像的实测拓扑；图注应保留“教学示意”。
- 若保留当前身份截图，只能承担“主机与板端不是同一系统”的例子，不得把它当作第5章烧录后镜像的验收结果。更严谨的做法是把真实板端身份图也移到第6章，在烧录后重新采集。

## 第4章可直接采用的最小准确概念文本

下面是一份不依赖 `pwd`、`ls`、`ps` 实测结果的最小文本。它可以替换当前4.3～4.5的操作性内容；Linux历史、Ubuntu/Buildroot关系可继续放在前面。

> Linux系统不只有内核。内核负责管理处理器、内存和驱动；Shell、基础命令、库、配置和应用位于用户空间。开发电脑上的Ubuntu用于准备构建环境，Buildroot也在开发电脑上运行；它生成适合嵌入式设备的内核、根文件系统和其他构建产物，板端运行的是这些产物，不是Buildroot构建工具。
>
> Linux把文件和系统接口组织在一棵从 `/` 开始的目录树中。`/etc`保存系统配置，`/bin`和`/sbin`提供基础命令，`/proc`和`/sys`提供运行中的内核与设备信息，`/dev`提供设备入口。它们的名字都出现在同一棵树里，但背后不一定来自同一块存储器，也不都对应eMMC中的普通文件。
>
> 程序开始运行以后形成进程，系统用PID区分每一次运行。进程名称只能说明观察时看到了这个对象，不能单凭名称判断它从哪里启动、是否长期稳定或业务是否正常。设备节点也只是应用进入驱动的一类入口；入口出现不等于对应硬件已经通过测试。
>
> 下一章先确认构建产物和烧录路径。镜像启动以后，第6章再登录当前板卡，用真实终端确认目录、进程和挂载状态，然后逐项测试硬件资源。

这四段已经足够支撑第5章和第6章，不需要在第4章给任何命令输出，也不需要用概念图冒充终端证据。

## 必须同步调整的上下游文字

1. **第3章结尾**当前写“下一章先登录boomPI，在真实终端观察目录、进程和存储空间”。后移后应改为：“下一章先分清Linux内核、Ubuntu主机和Buildroot构建工具；构建与烧录完成后，再在第6章登录板卡观察目录和进程。”否则第3章会对第4章作出错误承诺。
2. **第4章标题与开头**不能再写“登录以后呈现成什么样子”“这一次只读取系统信息”。应改成概念目标，例如“先分清开发电脑、构建工具和板端系统分别承担什么职责”。
3. **第4章状态**不再因缺 `pwd/ls/ps` 截图而处于“待截图”；但若仍保留身份实测图，其哈希、裁切和来源登记门禁继续有效。
4. **第5章结尾**必须给出明确分支：烧录成功并完成启动门禁，才能进入第6章；若候选镜像仍未通过门禁，则第6章只能标注为“对板上既有镜像的观察”，不能写成“刚烧录镜像的验收”。

## 第6章的推荐开场顺序

`pwd`、`ls`、`ps`不是以太网、屏幕或相机测试，应放在所有硬件项目之前，作为第6章的“系统基线门禁”。推荐顺序：

1. 确认登录目标和测试身份；
2. 确认镜像、内核、用户空间和板卡资料版本；
3. 用 `pwd`、`ls /`确认Shell位置和根目录；
4. 用挂载表确认目录背后的文件系统；
5. 用 `ps`与 `/proc/1`确认一次进程快照；
6. 确认门禁通过后，再按存储、以太网、Wi-Fi、显示、触摸、摄像头等资源逐项测试；
7. 音频继续后置到第14章以后，不因第6章枚举出 `/dev/snd`而提前测试。

## 第6章必须补齐的证据闭环

### 1. 测试身份与镜像门禁

| 必须记录 | 最低证据 | 通过条件 | 禁止外推 |
|---|---|---|---|
| 测试对象 | 板卡/样机标识、连接方式、主机采集时间 | 能区分本轮样机和其他RV1106板 | 主机名 `luckfox pico` 不能当正式板型 |
| 镜像身份 | 主机侧镜像文件名与SHA-256、构建记录或manifest、烧录结果 | 第5章确认的镜像与第6章测试对象一致 | 只看 `/etc/os-release` 不能证明源码与配置可复现 |
| 板端身份 | `cat /etc/hostname`、`uname -srmo`、`cat /etc/os-release`、设备树model或等价只读信息 | 命令成功，输出与本轮镜像前提一致 | Linux 5.10.160不等于未修改上游5.10 |
| 硬件资料对应 | 当前 `netlist.json` SHA与镜像内硬件baseline/manifest | 哈希一致，或明确记录不一致并降级结论 | 当前旧baseline哈希与现用netlist不一致时，不能写“镜像与当前硬件资料已完全对应” |
| 时间轴 | 主机侧采集时间、时区和日志哈希 | 全部证据按主机时间排序 | 当前板端时钟曾停留在2021年，不能用它证明2026年的测试顺序 |

第5章若实际烧录了新镜像，上述门禁以及后面的目录、进程和硬件结果必须全部重跑；不得把2026-08-10既有镜像的旧快照直接贴到新镜像之后。

### 2. `pwd` 与根目录观察

建议在**板端登录终端**执行经过当前BusyBox环境核验的只读命令：

~~~sh
pwd
ls /
ls -ld / /etc /bin /sbin /proc /sys /dev /tmp /run
~~~

证据必须同时包含：

- 完整命令、提示符、输出和退出状态/采集日志；
- 一张真实终端截图，能够看清 `pwd` 输出和 `ls /` 第一层名称；
- 一句判读：“`pwd`显示的是当前Shell所在位置，`/`才是根目录”，不得把登录目录和根目录混为一谈；
- 对当前实际存在目录的解释，不要求所有Buildroot镜像必须具有FHS中的每个可选目录；
- 隐私检查：裁掉密码、Wi-Fi信息、MAC、个人路径和不必要的IP地址。

通过条件不是“必须输出某个硬编码路径”，而是命令在当前镜像成功执行，输出能与本轮登录上下文对应，并能确认 `/proc`、`/sys`、`/dev`等本章要继续读取的入口存在。只读命令失败时先记录原始错误和 `command -v`/工具帮助，不执行 `apt install`，也不为补截图临时创建目录。

### 3. 挂载与目录来源

至少保存一次当前镜像的只读挂载快照：

~~~sh
cat /proc/mounts
cat /proc/partitions
~~~

应把“目录名”“挂载来源”“文件系统类型”分开记录。`rw`只表示当前挂载标志，不代表建议写入、掉电安全或介质健康；`df`容量也不能代替标称容量、坏块或全盘测试。若 `/proc`未挂载或内容异常，应停止后续硬件测试并回到启动/镜像门禁，不在教学流程中临时执行 `mount`修补状态。

### 4. `ps` 与PID 1观察

使用当前板已核验可用的命令形式，不照搬Ubuntu/GNU专用选项。现有证据见过 `ps -ef`，建议闭环为：

~~~sh
ps -ef
cat /proc/1/comm
cat /proc/1/status
~~~

截图至少显示 `ps`表头、PID 1所在行以及 `/proc/1/comm`结果。通过条件是三项输出彼此一致；可写“本次快照中PID 1名为init”。不得仅据名称写成“已确认BusyBox init”、不得把固定PID赋给普通服务，也不得把进程存在写成服务健康、自启动配置正确或长期稳定。`ps`命令行可能带敏感参数，公开截图前必须逐行审查；禁止读取或发布 `/proc/<pid>/environ`。

### 5. 原始记录、截图与判定三件套

每一组操作至少保留：

1. 原始文本日志，含命令、标准输出、标准错误、返回码和主机采集时间；
2. 当前真实终端截图，不能把日志重新排版成“终端图”；
3. 一条范围准确的PASS/FAIL/BLOCKED判定，以及对应失败恢复方向。

截图用于学生对照，原始日志用于审计，两者不能互相代替。发布版可脱敏，内部原始证据应保留哈希与采集说明；任何密码、密钥和真实Wi-Fi配置均不得进入仓库。

### 6. 后续硬件资源最低闭环

| 资源 | 第6章最低证据 | 当前已有边界 / 仍需补齐 |

| eMMC/SD | 动态发现块设备与挂载点；限定目录、限定大小的临时文件写入/回读哈希；清理结果 | 旧证据各有一次1 MiB受限读写PASS；若镜像重烧必须重跑，不能写整盘健康或掉电安全 |

## 现有证据能否直接搬到第6章

可以作为**历史/准备证据**引用，但不能自动成为第6章最终证据：

- `board-baseline-raw.txt` 能支撑旧镜像的一次系统、挂载和节点快照；
- `board-topology-raw.txt` 能支撑旧镜像的一次 `ps -ef` 与PID 1名称；
- `technical-verdict.md` 已给出以太网、Wi-Fi、存储、触摸、显示、摄像头和音频的有限判定；
- 上述记录均受当时镜像、板端状态、错误板端时钟和旧netlist哈希约束。

因此，第6章可以先用它们设计脚本和判定表，但只要第5章改变了镜像，最终正文必须使用新镜像下重新采集的真实命令、输出、截图和哈希。

## 最终建议

执行后移时，不应只删除第4章三条命令然后结束。完整调整应同时做到：

- 第4章改成纯概念章，不再声称完成板端目录/进程观察；
- 第3章结尾不再承诺第4章登录实操；
- 第5章解除HelloWorld板端运行对第6章终端基础的倒序依赖；
- 第6章新增“登录与系统基线门禁”，先完成身份、目录、挂载和进程闭环，再进入硬件；
- 第5章若烧录新镜像，第6章全部证据随镜像重采；
- 音频继续放在课程最后阶段。

满足以上条件后，后移方案在技术准确性、证据可追溯性和初学者认知顺序上均优于把无截图的 `pwd`/`ls`/`ps` 留在第4章。
