# 第4章《Linux系统简介》连续叙事计划

## 1. 本章位置与主线

第3章已经解释操作系统为什么需要管理处理器、内存、外设和文件，并用一次板端快照确认当前样机曾显示 `Linux 5.10.160`、`armv7l`、`Buildroot 2023.02.6`，PID 1显示为`init`。第4章不再重复“操作系统是什么”，而是回答一个更具体的问题：**登录一块已经运行Linux的boomPI以后，终端里出现的版本、命令、目录、进程和设备入口分别属于系统的哪一层。**

整章只走一条线：

> 终端同时出现Linux与Buildroot → Linux最初指内核 → 内核与用户空间被装成不同系统 → 登录当前板确认身份 → 从根目录观察用户空间和内核入口 → 用进程与设备节点看见系统正在工作。

本章建议保留5个二级标题。历史不是独立年表，发行版不是品牌清单，命令也不拆成“功能—格式—参数—实例”的词典。每个命令都只为回答当前段落中的一个问题。

章首可直接承接第3章：

> 上一章的板端快照里同时出现了`Linux 5.10.160`和`Buildroot 2023.02.6`。如果Linux就是整套系统，为什么终端还会报出另一个名字？要看懂这个结果，先要分清Linux这个名字最初指什么，以及开发板上的命令和目录从哪里来。

## 3. 建议的5个二级标题

### 4.1 Linux这个名字最初只指内核

本节从章首已经出现的两个名字起笔，不从“什么是Unix”开始。

主要段落逻辑：

1. 先指出终端中的`Linux 5.10.160`是内核身份。第3章已经说明内核管理处理器、内存和设备，本节只把“Linux”这个名称收窄，不重复内核模块清单。
2. 用两段完成最短历史：Linux在1991年以一个可在个人计算机上运行的内核项目起步，随后由全球开发者持续改进；它本身不是今天看到的桌面、终端命令或整套目录。确切日期和人物表述在正文前以kernel.org、Linux基金会或原始发布资料复核，不在本章扩写Unix分支史。
3. 再说明一个内核要变成可使用的系统，还需要命令、程序、库和配置。GNU及其他开源项目提供了许多用户空间工具，但本章不讲GNU历史、许可证和“GNU/Linux”命名争论。
4. 收回当前板：`uname`报告内核，不能据此知道板上有哪些命令；这正是下一节要解释的“内核之外还有什么”。

建议图片：

- 图4-1使用一条很短的教学时间线，只保留“早期Linux内核项目—社区持续开发—与用户空间软件组成可用系统”三格。图片不得画Unix家谱，也不列几十个年份和发行版标志。
- 图注写“教学时间线，说明Linux名称从内核项目延伸到日常所说的Linux系统”，来源绑定一手历史资料，不作为boomPI板端证据。

自然过渡：

> 内核负责底层资源，却不提供终端里全部命令。把内核、库、命令和配置组织到一起以后，用户实际拿到的才是一套可以使用的Linux系统。

### 4.2 同样使用Linux，系统为什么看起来不同

本节同时讲发行版、内核与用户空间，避免把三者拆成三个定义小节。

主要段落逻辑：

1. 先给“用户空间”的人话含义：内核之外，普通程序运行的区域叫用户空间；Shell、`ls`、`ps`、系统服务和项目应用都在这里运行，它们通过内核使用硬件。
2. 再给发行版：有人把选定的Linux内核、用户空间软件、安装和更新方式整理成一套可使用的系统，这类成品通常称为Linux发行版。这里只用Ubuntu作读者可能见过的例子，不列Debian、Fedora、Arch等族谱。
3. 解释嵌入式差异：桌面电脑重视通用软件和图形环境，开发板更在意镜像大小、启动速度和只保留需要的程序，因此两者都使用Linux，登录后看到的命令数量和目录内容仍会不同。
4. 准确处理Buildroot：Buildroot是开发主机上用来构建嵌入式Linux系统物料的工具，不是板上长期运行的内核或后台服务。当前板`/etc/os-release`曾显示Buildroot 2023.02.6，只能说明这套用户空间的构建来源标识；不能据此证明当前工作区能够逐字节复现正在运行的镜像。
5. 用一句话钉住关系：当前boomPI一次快照可读成“厂商Linux 5.10.160内核 + Buildroot构建的用户空间”，但内核补丁、配置和具体程序仍要分别核对。

建议图片：

- 图4-2只画上下两层：下层“Linux内核”，上层“库、命令、服务、应用（用户空间）”；右侧用小括号说明“Ubuntu把它们组织成桌面/通用系统，Buildroot用于构建精简嵌入式系统”。
- 不放Ubuntu桌面截图与大量发行版Logo，它们既不帮助读者理解当前板，也会把章节带成品牌介绍。

自然过渡：

> 名称分清以后，下一步不靠猜测判断当前板装了什么，而是登录终端，让内核和用户空间分别报告自己的身份。

### 4.3 登录以后，先确认正在看的系统

本节是从概念转入真实板端的节点。正文从“已经建立的终端会话”开始，不在这里配置RNDIS、静态IP、路由器或防火墙，也不把SSH成功写成以太网测试通过。

主要段落逻辑：

1. 先让读者看提示符，说明提示符只表示Shell正在等待输入。`#`通常表示当前会话具有root权限，`$`通常表示普通用户；实际用户名与主机名以当前提示符和命令输出为准，不套用Luckfox参考稿的账号。
2. 第一组观察只回答“内核是谁”：执行`uname -srmo`，从结果中只读出Linux、版本、armv7l和GNU/Linux；不把版本号解释成安全支持期限，也不把armv7l扩写成完整CPU性能。
3. 第二组观察只回答“用户空间由谁组织”：执行`cat /etc/os-release`，只读`NAME`、`VERSION_ID`或`PRETTY_NAME`。若字段不同，就记录真实结果，不要求读者把输出改成文档示例。
4. `cat /etc/hostname`只显示系统主机名。当前输出中的`luckfox pico`来自镜像配置，不能据此把当前硬件重新认定为Luckfox官方板。
5. 图后立即用三句判读：`uname`看内核，`os-release`看用户空间身份，`hostname`看当前系统名称；三条输出都不能证明摄像头、网络、屏幕或音频已经通过功能测试。

建议图片：

- 图4-3使用当前`assets/evidence/terminal-board-identity.png`的派生裁剪，只保留`hostname`、`uname`和`os-release`命令及输出。裁掉eth0地址、`carrier=1`、采集提示和“完成本关”等文字，避免提前进入网络测试或讲义式验收口吻。
- 若该素材并非直接终端抓屏而是从原始日志重排，图注必须写“板端证据终端摘录”，不能冒充现场终端截图。原始日志继续绑定`20260810-dhcp-recovery/board-baseline-raw.txt`及哈希。

失败恢复只放一小段，不另设“失败怎么办”标题：没有提示符时停止输入命令，先保留屏幕状态；出现`command not found`时不要安装软件，改用本章已在当前镜像核过的基础命令；输出与示例不同先截图记录，不通过改系统文件来“做成一样”。

自然过渡：

> 身份已经确认，但这仍只是几行名称。用户空间真正包含哪些程序和配置，要从Linux唯一的一棵目录树开始看。

### 4.4 所有内容从一棵目录树展开

本节承接第3章的根文件系统，不再解释bootfs/rootfs启动链。

主要段落逻辑：

1. 先从当前位置开始：`pwd`显示Shell此刻位于哪个目录；`ls /`列出根目录下的第一层内容。先让读者看到结果，再说明Linux用`/`表示整棵目录树的起点。
2. 与Windows的差别只用一段：Linux不为每个分区建立C盘、D盘式的独立树；不同存储和虚拟文件系统会接入这棵树中的某个目录。此处不讲分区地址、容量、ext4参数和读写测试。
3. 只选当前叙事需要的目录：`/bin`放基础命令，`/etc`放系统配置，`/dev`放设备入口，`/proc`提供进程和内核运行信息，`/sys`呈现设备与驱动关系。`/tmp`、`/oem`、`/userdata`若当前截图出现，只解释为当前系统中的目录/挂载位置，不把Luckfox旧文档的用途直接套到boomPI。
4. 用`ls -ld /dev /proc /sys`让读者看到三者都位于根目录下；随后说明它们看起来像目录，但内容有一部分由内核运行时提供，不等同于eMMC里预先存放的普通文件。
5. 停在“目录把不同来源的内容接到一起”。`df`、`mount`、分区表、文件系统类型和容量验证后移到第5章镜像/文件系统闭环或第6章存储测试，避免本章从认识目录突然跳到存储验收。

建议图片：

- 图4-4必须是当前板真实终端截图，连续保留`pwd`、`ls /`、`ls -ld /dev /proc /sys`及输出。图前告诉读者只找根目录、三个入口；图后只给上述三个结论。
- 可在截图旁放一条极简树形示意：`/ → bin、etc、dev、proc、sys`。示意图不能列二十多个目录，也不能用其他开发板的根目录截图填空。

自然过渡：

> `/bin`和`/etc`主要保存程序与配置，`/proc`、`/sys`和`/dev`则会随着系统当前状态变化。顺着这三个入口，可以看见第3章讲过的进程和驱动怎样出现在Linux里。

### 4.5 进程和设备怎样出现在这棵树里

本节把第3章的进程概念落到当前系统，再把设备节点放到明确的证据边界内；不做任何硬件功能测试。

主要段落逻辑：

1. 执行当前镜像已验证可用的`ps -ef`，只读表头和前几行：PID是这一次运行的编号，PPID表示它由哪个进程启动，COMMAND显示正在运行的程序。不要逐项解释全部内核线程。
2. 用`cat /proc/1/comm`或本轮重新核验过的等价只读命令观察PID 1。若结果仍为`init`，正文只能写“这次快照的PID 1名为init”；未解析`/proc/1/exe`和Buildroot配置前，不写成确定的BusyBox init、systemd或SysV init。
3. 再回到`/dev`：设备节点是程序请求内核驱动的入口，外观上可以像文件一样被列出，但它不是设备本体，也不等于数据一定可读。
4. 只选`/dev/null`、`/dev/console`或本轮重新确认的两个通用节点说明字符设备标记；不要在本章枚举`/dev/video*`、`/dev/input/event*`、`/dev/snd/*`并顺势宣称摄像头、触摸或音频可用。
5. 明确三档结论：目录存在只能证明入口存在；节点出现通常说明内核创建了接口；真正功能是否正常还要在第6章用对应硬件、命令和结果逐项测试。
6. 收章时回到最初的两个名字：内核提供进程、设备和文件系统接口，Buildroot构建的用户空间提供Shell和命令。读者现在能够在终端里区分“谁报告内核”“谁报告用户空间”“哪些目录反映运行状态”。

建议图片：

- 图4-5使用当前板真实终端截图，上半显示`ps -ef`前若干行和PID 1，下半显示`/proc/1/comm`以及`ls -ld /dev /proc /sys`或少量通用节点。若一张图中文字太小，就拆成上下两张连续大图，不并排缩成无法阅读的小图。
- 图后必须紧跟一句：“本图只证明一次进程快照和入口存在，不是外设功能验收。”

章末自然进入第5章：

> 当前系统的内核、用户空间、目录和进程已经能够在终端中对应起来。下一章再回答这些内核与用户空间文件怎样被构建成固件并写入板上存储；在那之前，本章不修改分区，也不执行烧录。

## 4. 命令与截图的最小闭环

| 观察问题 | 建议命令 | 截图后只写什么 | 本章禁止外推 |
|---|---|---|---|
| 当前内核是谁 | `uname -srmo` | 一次输出中的内核名、版本和体系结构字符串 | 内核安全支持、实时性、补丁集、所有驱动可用 |
| 当前用户空间怎样自报身份 | `cat /etc/os-release` | 当前字段显示的NAME/VERSION | Buildroot在板上“运行”、当前工作区可复现镜像 |
| 当前主机名是什么 | `cat /etc/hostname` | 镜像配置的主机名 | 主机名等于硬件型号 |
| Shell现在位于哪里 | `pwd` | 当前工作目录 | 分区和挂载健康 |
| 根目录第一层有什么 | `ls /` | 一棵目录树的入口 | 每个目录固定来自eMMC或固定用途 |
| 运行状态入口在哪里 | `ls -ld /dev /proc /sys` | 三个入口均位于根目录下 | 节点存在即硬件通过 |
| 当前有哪些进程 | `ps -ef` | PID、PPID、COMMAND的最小含义 | 一次进程表等于自启动/稳定性验收 |
| PID 1叫什么 | `cat /proc/1/comm`，须本轮重核 | 一次结果中的进程名 | 未取证前指定init实现 |

操作截图统一遵循参考文档中“先说为什么执行—给命令—紧邻截图—指出读哪一行”的节奏。不要把八条命令排成一个长代码块后再集中解释，也不要给每条命令拆出“命令功能、命令格式、参数说明、使用实例”四个三级标题。

## 7. 低AI味门禁

正文中删除或改写以下模式：

- “Linux就像一座城市”“内核是大管家”“目录树像一棵大树”等连续类比。目录树本身是正式结构，直接画出`/`即可。
