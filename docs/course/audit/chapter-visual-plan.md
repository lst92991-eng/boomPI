用途：给正文作者、截图采集者和最终排版者使用；本文件只规划图片，不替代正文、实测记录或证据台账。

## 1. 先给结论

这套文档不能靠“多画几张架构图”补足。最需要补的是读者自己可以照着做、并能看见成功或失败的真实画面。建议全书采用三种明确分开的图片：

1. **认识对象**：boomPI 实物、芯片手册、干净原理图、源码位置。回答“这是什么、在哪里”。
2. **完成动作**：Windows、Ubuntu、板端、手机上的真实操作截图。回答“我现在点哪里、输入什么”。
3. **确认结果**：终端输出、设备实拍、程序页面和失败分支。回答“做到什么样才算完成”。

当前没有找到可确认属于 boomPI 的整板正反面照片。工作区中的 Luckfox Pico Ultra / Ultra W 图片只能作为参考文档的来源对象，**不得作为 boomPI 实物图**；`camera-frame-576x324.png` 是 boomPI 相机采到的现场画面，也不是整板照片。第 1 章在取得真实照片前必须保留明确图位，不能用别的 RV1106 开发板顶替。

最新视觉约束优先级如下：

- 原理图只放源图整页或干净局部裁剪，**不加红框、箭头、编号框**。读者定位靠紧邻的标题、图注和正文，不在原理图上做二次标注。
- GUI 操作图可以使用少量红框、箭头、步骤号；一次只强调一个动作，连续动作分成两图。
- 终端截图不画装饰框。必须让命令、关键输出和本节结论同屏；日志查看器画面只能写“本轮证据终端摘录”，不能冒充原始板端交互。
- 一张图只承担一个问题。操作型页面以每页 1 张大图或 2 张上下连续图为宜；不沿用参考文档中一页塞 4～10 张图的高密度做法。
- 图片不能证明的事情不写成“通过”。原理图只能证明设计连接；Host 测试只能证明主机测试；显示命令已发出不能代替屏幕肉眼确认。

### 2.3 本项目的截图和图注合同

每个操作图组固定写成下面五行，允许其中“失败怎么办”在很简单的步骤省略，但不能省略结果：

1. **目的**：这一小步解决什么问题。
2. **操作**：点击位置或可复制命令。
3. **图片**：动作后的真实状态，必要时另放动作前状态。
4. **看到什么算成功**：写人能判断的可见结果，不只写退出码。
5. **失败怎么办**：就近给一个最可能原因和下一条检查命令。

统一图注格式建议为：`图 章-序号　动作或对象——可见结果（证据范围）`。例如：`图 6-08　写入并读回 SD 卡测试文件——大小和 SHA-256 一致（本轮板端实测，只覆盖本次 1 MiB 检查）`。

隐私最低要求：Windows 用户名、主机名、本机绝对路径、IP/MAC、Wi-Fi SSID/密码/二维码、API Key/token、设备序列号、SSH/TLS 指纹、私有域名、通知、人脸、屏幕反光和现场背景均需检查。能不用真实秘密就不用；必须显示网络结构时只保留教学所需的网段或占位符。

## 6. 采集和排版验收清单

每张新图进入正文前逐项确认：

- [ ] 图能回答一个明确问题，且正文在图片前告诉读者要看哪里。
- [ ] 操作图同时具备动作、结果和通过/失败判断；关键步骤有动作前状态。
- [ ] Windows、Ubuntu、板端、手机、实物环境在图注中写清楚。
- [ ] 终端是真实执行窗口；证据摘录已按“本轮证据终端摘录”命名。
- [ ] 命令、关键输出、退出状态或人工判定没有被裁掉。
- [ ] 原理图完全无红框、箭头、编号框；图旁有源 PDF 页码和模块名。
- [ ] 手册裁剪紧邻对应原理图；注明手册名称、版本、页码。
- [ ] Host、设计资料、历史记录、板端实测、声学 HIL 的证据等级没有混写。
- [ ] 主板 BOM 与外接屏、触摸、相机、扬声器、麦克风、SD 卡、USB 设备已分清。
- [ ] 图片已检查用户名、主机名、路径、IP/MAC、SSID/密码、二维码、Key/token、指纹、域名、设备 ID、通知、反光、人脸和环境。
- [ ] 每页通常不超过 1 张大图或 2 张连续图；图片按正文同流内嵌，居中，图注紧随。
- [ ] 失败图有恢复步骤；会改写镜像、配置、证书、mixer 或产生声音/录音的动作已取得授权。

完成上述队列后，视觉主线应该是：先看真实板和手册，随后只读原理图；再在 Windows/Ubuntu 完成固件和程序，在板端逐项看见硬件结果；最后才进入音频和整链 HIL。这样即使读者害怕技术词，也可以每次只完成一个小动作，并用紧邻的真实画面判断自己是否走对。
