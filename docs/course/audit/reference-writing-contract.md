## 1. 什么是本地参考文档中的“低 AI 味”写法

### 1.1 低 AI 味来自真实教学动作，不来自刻意口语化

参考文档最自然的地方，往往不是用了“我们”“同学”之类的称呼，而是教师真的替读者预判了下一步会遇到什么。例如登录文档在密码界面之后立即说明“输入密码时，屏幕上不会有任何显示，这是正常现象”。这句话没有比喻，也没有情绪安抚，却能防止读者误以为键盘失灵。

合格写法应满足：句子中出现一个具体对象、一个当前动作或现象、一个可用于判断的结果。只有“别担心”“这一步很重要”“后面会详细介绍”而没有对象和结果，不算教师口吻。

### 1.2 每一段只把当前问题向前推进一步

本地参考的操作段落常见节奏是：先说为什么要做，再给一个动作，图中显示动作后的界面，紧接一句说明读者应看到什么。它不是把“目标、准备、操作、预期、失败、小结”机械做成六个标题。

新稿正文采用下列局部节奏，但只把它当作段落组织原则：

1. 当前卡在哪里，为什么要做这一步。
2. 执行一个可以当场完成的动作。
3. 放与该动作相邻的真实截图或干净原理图模块。
4. 指出图中应关注的位置或终端中应出现的两三行。
5. 用看到的现象得出一个结论，再进入下一步。

如果一个动作需要两张以上截图，先拆动作，不要让一张图同时承担下载、安装、配置和成功验证。

### 1.3 标题负责维持大方向，动作留在正文里完成

参考材料的好处是读者能够快速定位“烧录”“登录”“SDK 编译”“文件系统”等大任务；坏处是部分长项目文档把每个小动作也做成标题。boomPI 新稿只继承前者。

每章保留 4～8 个二级标题。一个二级标题应承载一个连续问题，通常包含至少两个自然段，或一组完整的“动作—图片—结果”。“打开软件”“点击按钮”“看到成功”不是三个标题，而是同一节中的三个动作。

正文最多出现三级标题。只有一段正文、只有一张图或只有一个命令的小标题，一律并回相邻内容。需要视觉停顿时用自然段、短引导句或图注，不继续增加标题层级。

### 1.4 专业词先解释用途，再给正式名称

读者害怕术语，不等于删掉术语。正确顺序是先回答“它在眼前这块板上负责什么”，再给名称，随后马上回到图或动作。

例如：

- 不先写“PHY、MAC、RJ45、MDI”。先写“网线里的电信号不能直接交给 Linux 程序，芯片内部先负责收发和转换”，再引出 MAC、PHY。
- 不先列 `MIPI CSI`、`I²C`、`MCLK`、`RESET`、`PWDN`。先把摄像头接口分成“搬图像、配置传感器、让传感器正确上电”三件事，再在对应原理图旁给出信号名。
- 不先定义 `rootfs`。先说“Linux 内核启动以后，还需要命令、库和配置文件”，再告诉读者这套目录叫根文件系统。

同一自然段原则上不首次引入超过两个缩写。确需出现更多名称时，先按用途分组，再逐组展开。

### 1.5 过渡必须来自前一步留下的实际问题

低 AI 味的过渡不写“接下来我们继续学习”。它应说明为什么自然要走到下一节。

可用的因果过渡：

- “电源已经按顺序稳定，芯片下一步要去哪里读取启动内容？”
- “系统能启动还不够，我们还没有办法从电脑进入板子。”
- “有线网络已经能访问局域网，下一步再处理不方便拉网线的场景。”
- “页面能显示以后，手指的坐标才有地方产生效果。”

不合格过渡只有课程自述，没有因果对象，例如“后续我们将进一步探索”“下一节继续学习相关知识”。

### 1.6 图片不是装饰，而是正文中的一次共同观察

每张关键图前要有一句话说明为什么现在看它；图后要有一句话说明读者从图中得到什么。操作图的前文给动作，后文给结果。原理图的前文给观察任务，后文指出器件、网络名和设计原因。

GUI 截图允许用少量红框、箭头和编号指示点击位置。原理图必须使用干净模块裁剪，不画框、不画箭头、不编号；芯片手册原页和对应原理图模块相邻放置，由正文说清“手册提出什么要求—本板用什么器件实现—为什么这样做”。

一张图只回答一个主要问题。图注写“图中是什么”，正文写“为什么此刻看它”和“看完得到什么”，不要把整段解释塞进图注。

### 1.7 操作说明必须包含可判断的终点

参考文档中最有用的句式是“如果能看到……说明……”。boomPI 后续每组命令都要有：

- 前置条件：当前在哪台电脑、哪个目录、板子是否在线、是否需要权限。
- 动作：一组最小命令或一个 GUI 操作。
- 预期：只摘录能判断成败的输出，不粘贴整屏日志。
- 常见失败：给最可能的 1～3 个原因。
- 恢复：告诉读者如何回到本节起点，而不是让其盲目重装、重刷或删除数据。

这些内容应自然分布在动作附近，不能每节都套同一组六个可见标题。

### 1.8 证据强度必须写进语气

手册只能证明芯片或器件具备能力；原理图和 netlist 只能证明设计连接；源码和配置只能证明实现状态；带时间、板卡、镜像和命令的当前日志才能证明本轮实测。

因此使用不同动词：

- 手册：`支持`、`规定`、`建议`。
- 原理图：`连接到`、`预留`、`选择了这条路线`。
- 源码：`实现了`、`配置为`。
- 当前板端证据：`本轮在……条件下看到`、`本轮验证通过`。

不得用“已经可用”“测试通过”把手册参数、源码默认值或历史 HIL 升格为当前板端结论。

## 2. 高 AI 味禁用模式与可执行改写规则

| 禁用模式 | 识别信号 | 强制改写动作 |
| --- | --- | --- |
| 课程自述代替内容 | “本章将”“我们会”“阅读顺序始终”“后续将详细介绍”连续出现 | 删除自述，直接写当前对象和眼前问题；全章路线只在开头用 1～2 句交代一次 |
| 固定六段模板 | 每节都出现“本节目标/准备/操作/看到什么/失败怎么办/小结/通关卡” | 这些字段只留在作者内审卡；正文按真实动作自然展开 |
| 空泛重要性 | “这一步非常重要”“值得注意的是”“显而易见”后面没有可观察对象 | 改成“若……，会看到……；此时先……” |
| 过量类比 | “像教室、管家、仓库、道路、门”连续出现 | 一个概念最多保留一个确实能减少认知负担的类比；能用物理因果说清就删类比 |
| 参数展柜 | 一个段落连续出现 5 个以上缩写、型号、单位或能力 | 只保留当前任务用得到的参数；按“用途—本板对应—设计原因”拆开；其余移到参数表或后文 |
| 三段式批量生成 | 大量“首先、其次、最后”“第一组、第二组、第三组”，段落长度和句式高度对称 | 用真实先后关系连接；没有时间或因果顺序的并列项改成一张小表或一句话 |
| 小标题碎片 | 标题后只有一段、一图或一条命令 | 合并回上一级；动作使用短引导句，不再建立标题 |
| 未来承诺链 | 一段不停列“后面会烧录、登录、测试、开发、接入……” | 只保留与下一章直接相关的一个桥；全课程路线放目录或前言 |
| 自我评价 | “这样安排的好处是”“这就是示范文档常用的方法”“本节帮助读者……” | 删除评价，直接呈现动作和结果 |
| 假安慰 | “不要担心”“非常简单”“严格照做就能成功” | 改为具体的异常表现、原因和恢复路径 |
| 伪实测 | 用源码参数、手册截图、旧日志或其他板卡照片写“验证成功” | 降级为相应证据能支持的表述，并登记缺失的当前实测 |
| 图后无结论 | 图片出现后直接换标题 | 图后补一段：指出关键位置、读出结果、说明下一动作 |
| 结尾口号 | “本章只需记住三句话”“至此我们已经掌握……” | 写本章真正关闭的闭环，再提出下一章必须解决的具体问题 |

### 2.1 对当前常见套话的直接替换

- `本章先从整板框图认识开发板，再看……` → `先看整板框图。图上每一条连接都从 RV1106G3 出发，分别通向电源、存储、网络和外接接口。`
- `阅读顺序始终沿着……展开` → 删除。结构应由标题和过渡自然呈现，不用正文自证。
- `可以把主控上电想成进入教室` → `核心电源尚未稳定时，高电压 I/O 不能先驱动芯片，因此几路电源需要按手册规定的顺序建立。`
- `本章只需记住三句话` → `电源稳定后，BootROM 开始查找启动介质；boomPI 把 Linux 镜像长期保存在 eMMC 中。`
- `这就是示范文档常用的读图方法` → `手册要求 FEPHY_EXTR 使用 6.04 kΩ 电阻，原理图中的 R46 与这一要求对应。`
- `对于初学者，本章先建立一个重要认识` → `原理图决定网络怎样连接；PCB 叠层和布线决定高速信号能否可靠传输。`

## 3. 逐章写作门禁

任何章节只有全部通过以下门禁，才可进入 DOCX 生成。任一项失败，状态保持“写作中”或“审校中”。

### G0：协作与原始资料门禁

- 已读取 `AGENTS.md`、`docs/course/AGENTS.md` 和最新 `docs/course/status/chapters.md`。
- 台账中有唯一章节作者，其他角色只读审校。
- 直接打开与本章最相近的 2～4 份原始 DOCX，记录文件名、页码和借鉴的具体行为。
- 已读取本章相关的原理图、netlist、官方手册、源码或板端日志，且没有只引用旧审计摘要。

失败条件：台账不存在、作者冲突、只读了二手摘要、使用了其他开发板的照片或命令。

### G1：连续叙事门禁

- 开头承接上一章留下的一个实际问题，不写空泛学习目标。
- 本章只有一条主线，并能用一句因果链概括。
- 结尾关闭本章动作，并把一个尚未解决的问题交给下一章。
- 全章保留 4～8 个二级标题；正文可见标题不超过三级。

失败条件：章节同时追两条无关主线；用课程路线替代本章叙事；标题后只有一段或一图；结尾突然换到远期功能。

### G2：段落与术语门禁

- 一段只承担一个中心意思。
- 超过约 160 个汉字的段落必须人工检查是否可在因果转折处拆分；不能为了数字机械切段。
- 同一段首次出现的缩写原则上不超过两个。
- 首次出现的术语先用一句人话说明用途，再给正式名称。
- 连续三段不得使用相同开头、相同总结句或高度对称的句长。

失败条件：参数与缩写排成墙；用三个以上类比解释一个简单事实；读者必须回看两段才能知道代词指什么。

### G3：概念章节门禁

概念章节按“用途—官方定义—本板对应—为什么这样设计”连续叙述。官方框图、手册要求和本板原理图必须真正对应，不能只在末尾堆来源链接。

失败条件：只抄芯片参数；只讲通用 Linux 百科；手册截图与原理图模块相隔数页；没有说明参数为何与本板相关。

### G4：操作章节门禁

每个关键动作附近必须同时存在：前置条件、动作、最小预期输出、常见失败和可逆恢复。危险动作另加影响范围和备份/退出路径。

命令块前写清在哪台机器、哪个目录、以什么身份执行；命令块后只保留用于判断的输出。不能用整屏日志代替“看到什么”。

失败条件：命令没有主机/目录；默认读者已安装工具；失败只写“检查环境”；恢复要求重刷、删数据或关闭安全功能却没有授权。

### G5：图片门禁

- GUI 关键动作有真实截图，点击位置可少量标注。
- 原理图使用干净模块裁剪，不画框、不画箭头、不编号。
- 手册原页/关键表格与对应原理图模块相邻。
- 每张图前有观察任务，图后有读图结论。
- 图中没有账号、密钥、Wi-Fi 密码、个人路径等隐私。

失败条件：用概念图冒充真实终端；用其他板卡照片；一张图承担多个动作；图后直接换标题；图片小到必须放大才能读字。

### G6：证据与事实门禁

- 每个结论标明属于手册能力、设计连接、源码状态、历史 HIL 还是当前实测。
- 当前实测包含日期、板卡、镜像/二进制、命令和结果。
- 历史 HIL 不绑定到新镜像或新二进制。
- 蓝牙、音频通道、摄像头、设备节点等不能根据相似板卡猜测。

失败条件：使用“已验证”却找不到当前证据；用“通常、一般、可能”反复掩盖资料不足；把外接器件写成主板贴片器件。

### G7：低 AI 味机械审查门禁

全文搜索以下词组并逐项人工判定：`本章将`、`我们将`、`后续会`、`接下来继续`、`值得注意的是`、`非常重要`、`可以把……理解成`、`首先/其次/最后`、`这样安排的好处`、`本章只需记住`、`至此我们已经`。

这些词并非绝对禁字，但每次出现都必须带来具体对象、动作或结果。只承担自述、评价、口号或填充作用时立即删除。

### G8：交付门禁

- 技术审校、可读性审校、视觉审校均已关闭高优先级问题。

## 5. 推荐的 18 章连续叙事结构

全书只走一条主线：先认识板子和 Linux 为什么能工作，再把镜像写进去并进入系统；随后逐项确认硬件资源；硬件无误后再搭项目、画页面、接网络服务；音频在最后一章一次完成。

| 章 | 章名 | 本章连续叙事与出口 |
| ---: | --- | --- |
| 1 | 开发板简介 | 从成品板能做什么出发，认识 RV1106G3、外围资源分工、电源顺序、eMMC、复用、信号与 PCB 注意事项。结尾留下问题：硬件都在，谁负责统一调度？ |
| 2 | 操作系统是做什么的 | 用“管理处理器、内存、文件和外设”解释 OS，不先堆 U-Boot/内核名词。再说明一块板从上电到应用运行需要多层软件，结尾引出本板选择 Linux。 |
| 3 | 在 boomPI 上认识 Linux | 从读者登录后会看到的目录、命令、进程和设备文件解释 Linux。只做安全、只读的小练习，结尾指出这些软件对象最终都要对应到原理图里的硬件。 |
| 4 | 从芯片手册读回 boomPI 原理图 | 按电源、启动存储、网络、屏幕触摸、摄像头、扩展口逐模块阅读；每个模块都采用“手册要求—本板电路—设计原因”。结尾确认烧录入口和目标存储。 |
| 5 | 把系统镜像烧进开发板 | 解释镜像、电脑驱动、烧录模式和目标存储；用真实 Windows/Ubuntu 截图完成识别、选择镜像、写入、完成验证和失败恢复。结尾让板子第一次从新镜像启动。 |
| 6 | 第一次启动并登录板子 | 观察启动信息，确认板卡和镜像身份；再通过已验证的串口/ADB/SSH 路线进入系统。明确密码无回显、DHCP 地址和登录失败恢复，结尾取得稳定命令行。 |
| 7 | 文件放在哪里，怎样传到板子上 | 用 `/tmp`、持久化分区和重启实验解释存储；完成文件查看、传输、权限、时间和最小日志操作。结尾得到后续测试可复用的文件传输路径。 |
| 8 | 先把有线网络跑通 | 插线、获取 DHCP 地址、确认链路、`ping` 局域网主机和访问本地服务；每一步都有当前板端证据。结尾得到可靠的开发通道，再处理无线场景。 |
| 9 | Wi-Fi 接入与蓝牙通路核对 | 先确认 U15 选择和 Wi-Fi USB 枚举，再完成扫描、连接、断线恢复和配置保存。蓝牙只按原理图闭合路线和当前系统枚举下结论，证据不足就明确“本轮不宣称可用”。 |
| 10 | 让屏幕先显示一张可靠画面 | 确认显示设备和背光，显示测试色、图片和方向标记，再处理亮度与刷新。结尾只证明“能稳定显示”，不提前进入 LVGL 项目页面。 |
| 11 | 让触摸坐标与屏幕对上 | 先确认触摸设备，再读取原始事件、核对四角方向和坐标范围，最后完成一次“按哪里、哪里响应”的小闭环。结尾为后续 LVGL 交互准备输入通道。 |
| 12 | 摄像头从识别到单帧预览 | 先确认传感器和驱动，再采一帧、检查格式/分辨率并显示真实画面，最后做有界连续预览。硬件预览通过不写成视觉 AI 已完成。 |
| 13 | 我们要做一个怎样的 boomPI 项目 | 用用户实际会经历的流程定义需求：开机、联网、界面状态、服务连接、对话和错误恢复；明确当前版本做什么、不做什么。结尾形成可逐项验收的最小产品路径。 |
| 14 | 项目由哪些程序一起完成 | 用人话解释板端客户端、本地 Go 服务、网络、UI 和配置各自负责什么，再给源码目录、构建入口和部署位置。结尾形成“改一处—编译—传输—运行—看结果”的开发循环。 |
| 15 | 先画出第一版 LVGL 页面 | 从静态布局开始，依次放状态文字、主要按钮/区域和必要图标；在真屏上核对字号、颜色、方向和刷新。此时不接音频，只让页面可靠显示当前状态。 |
| 16 | 让触摸真正推动页面状态 | 把第 11 章的触摸输入接入 LVGL，完成页面切换、音量/亮度控件和错误提示；所有 LVGL 对象只由 UI 线程访问。结尾得到可操作但尚未联网的产品外壳。 |
| 17 | 配网、发现服务并跑通文字链路 | 先用有线网络验证服务端，再完成已保存 Wi-Fi/首次配网入口、服务发现、加密连接和配置持久化；用文字请求替代声音验证一次完整请求—回复—字幕状态链。结尾只剩声音输入输出。 |
| 18 | 最后实现音频与完整语音对话 | 顺序固定为：数字声音基础 → 只播放 → 只采集 → 有界队列 → VAD/唤醒 → 3A → 一问一答 → 三秒追问 → 播放中打断。Mode1、4 通道和 3A 只在授权 HIL 中下结论，并记录资源所有者、隐私、音量、时限、mixer 保存/恢复、dry-run 和证据绑定。 |

### 5.1 全书顺序的硬约束

1. 第 7～12 章是硬件资源逐项测试，必须位于项目开发之前。
2. 第 13 章之后才进入项目需求、架构和复现流程。
3. LVGL 静态页面先于配网和服务链；文字链先于音频链。
4. 音频只在第 18 章展开，前文最多说明接口位置和课程顺序，不讲实现细节。
5. 单项硬件测试通过不等于项目集成通过；摄像头预览不等于视觉 AI，Wi-Fi 枚举不等于稳定联网，源码参数不等于音频 HIL。
