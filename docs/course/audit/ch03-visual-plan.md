# 第 3 章《操作系统简介》视觉计划

## 1. 结论

本章建议 **6 张必需图 + 1 张可选实测图**，不使用来源不明的网络图片，也不直接搬运参考 DOCX 中来源不明的概念图。六张必需图均采用“项目自制、官方资料校核事实”的方式：图面只保留当前段落必须理解的关系，正式术语放在生活化解释之后。

推荐顺序如下：

1. 图 3-1：一次触摸请求怎样经过 OS 再返回；
2. 图 3-2：Linux 的用户空间与内核空间；
3. 图 3-3：一个 CPU 怎样轮流运行多个进程；
4. 图 3-4：每个进程看到的内存与实际内存；
5. 图 3-5：嵌入式 Linux 系统由哪些文件和角色组成；
6. 图 3-6：从按下电源到应用出现的启动链；
7. 图 3-7（可选）：本轮样机读取到的 Linux/Buildroot 身份。

这套图的作用不是替代正文，而是分别回答六个问题：“OS 在哪一层”“应用怎样找内核办事”“多个程序为什么能一起跑”“内存为什么不会被程序随便踩”“镜像里有哪些角色”“开机时这些角色按什么顺序接力”。

## 3. 官方资料检索结论

本轮只采用官方一手资料核对事实：

- Linux 内核的[用户空间 API 指南](https://docs.kernel.org/userspace-api/index.html)列出系统调用以及设备/I/O 用户接口，可支撑“应用通过受控接口请求内核服务”。
- Linux 内核的[新增系统调用说明](https://docs.kernel.org/process/adding-syscalls.html)把系统调用说明为用户空间与内核之间最传统、最明显的交互点；因此图 3-2 可以用“系统调用/API”作为门，而不把应用箭头直接画进驱动。
- Linux 内核的[调度器索引](https://docs.kernel.org/scheduler/index.html)和[EEVDF 调度器说明](https://docs.kernel.org/scheduler/sched-eevdf.html)说明当前调度器存在不同策略，并会在可运行任务间分配 CPU 时间。图 3-3 只能表现“CPU 的运行权会在任务之间切换”，不能声称 Linux 永远按固定时间片、固定 A→B→C 顺序调度。
- Linux 内核的[虚拟内存概念说明](https://docs.kernel.org/admin-guide/mm/concepts.html)说明虚拟地址会被翻译为物理地址、不同虚拟页可映射到物理页，并具有隔离和受控共享的作用。
- U-Boot 的[Standard Boot Overview](https://docs.u-boot.org/en/stable/develop/bootstd/overview.html)说明 U-Boot 可从介质寻找启动流程，并按启动描述装载 kernel、initrd 和 Device Tree 文件。它是启动链的事实依据，不代表 boomPI 必然使用文档中的某一种标准启动配置。
- Linux 内核的[init 启动故障说明](https://docs.kernel.org/admin-guide/init.html)明确把挂载 rootfs、找到并装载 init 作为关键步骤。
- [Buildroot 官方手册](https://buildroot.org/downloads/manual/manual.html)说明 Buildroot 可以生成交叉工具链、rootfs、Linux kernel image 和 bootloader，并明确这些是不同产物。它适合校核图 3-5，不适合整页截图给初学者阅读。

这些官方页面以英文正文、目录和代码为主，本轮没有发现一张同时满足“中文初学者可读、低密度、能直接对应 boomPI”的官方总览原图。因此 **不建议把官方网页截图当正文主图**。更合适的做法是依据其事实自制中文小图，并在图注或章末来源表中给出链接。Linux 内核整体采用 GPL-2.0-only；Buildroot 手册页面明确标注 GPLv2；U-Boot 页面标注社区版权。若未来确需转载原页，应单独核对具体源文件的 SPDX/许可并保留版本、标题和链接，本计划不以“教学用途”代替版权核验。

## 4. 逐图制作计划

### 图 3-1　一次触摸请求怎样经过 OS 再返回

- **正文作用**：在第一次出现“操作系统”时，只回答“它位于应用与硬件之间，并负责把请求送下去、把结果送回来”。这是全章主锚点。
- **画面内容**：三层横条，从上到下为“应用：页面等待一次触摸”“操作系统：安排请求、调用驱动、返回事件”“硬件：触摸屏/控制器”。一根向下箭头写“读取触摸”，一根向上箭头写“返回触摸事件”。不要展开 CPU、内存、文件系统等术语。
- **来源**：事实依据为 Linux 内核用户空间 API 指南与驱动模型；本地 `tmp/boompi-doc-v4/figures/03-os-concept.png` 及生成脚本 `tmp/boompi-doc-v4/create_figures.py` 可作构图草稿。
- **制作方式**：用项目绘图脚本重制 1600×900 或等比例 PNG；白底、三种低饱和色、无装饰图标、无大标题。不要直接使用现有 v4 图，因为它是满页海报，信息和口号过多。
- **图前动作/图后判定**：图前问“页面想知道手指点在哪里，为什么不直接读一根线？”；图后只收束为“应用提需求，OS 管过程，硬件完成实际动作”。
- **版权与证据标签**：项目自制原创构图；官方资料只作事实依据；图注标 `[教学示意]`，不标 `[本轮实测]`。
- **替代文本**：`应用向下发出读取触摸的请求，操作系统调用硬件；触摸结果再经操作系统返回应用。`
- **禁写**：不要写“OS 会保证所有请求成功”；不要把驱动画成板外硬件；不要使用 Windows、Android 或手机外观图标。

### 图 3-2　Linux 的用户空间与内核空间

- **正文作用**：把“OS”过渡到 Linux 的正式边界，解释应用为什么不能随意操作全部内存和设备。
- **画面内容**：上半区“用户空间”只放两个例子：boomPI 应用、命令行工具；中间是一条清晰边界，门上写“系统调用 / 受控接口”；下半区“内核空间”只放四个小块：进程、内存、文件、设备驱动；底部用一条细线接“硬件”。
- **来源**：Linux 内核用户空间 API 指南、Linux 内核新增系统调用说明、Linux 内核 Device Model 文档。
- **制作方式**：项目自制两区剖面图。用户空间和内核空间各用一种底色；跨界只保留一组双向箭头。不得照抄内核官网排版，也不得使用来源不明的“Linux architecture”网络图。
- **图前动作/图后判定**：图前从“应用不能直接决定谁先用 CPU”引入；图后让读者能指出“应用在上方，内核管理资源，系统调用是入口”。
- **版权与证据标签**：项目自制；事实引用官方内核文档；图注标 `[教学示意]`。
- **替代文本**：`用户空间中的应用和命令行工具通过系统调用进入内核空间，内核负责进程、内存、文件和设备驱动。`
- **禁写**：不要把 libc、VFS、调度类、页表层级或中断链全部塞入；不要说系统调用是用户空间和内核之间“唯一”接口。

### 图 3-3　一个 CPU 怎样轮流运行多个进程

- **正文作用**：解释“多个程序看起来同时运行”来自调度，而不是每个程序永久占着一颗 CPU。
- **画面内容**：左侧列出三个具体任务：“界面刷新”“网络收发”“相机取帧”；右侧只有一条 CPU 时间轴，用不同色块表示某段时间正在运行 A、B 或 C，空白/等待用浅灰表示。旁边放一句小字：“顺序和时长由调度器决定”。
- **来源**：Linux 内核调度器索引及 EEVDF 调度器说明。
- **制作方式**：项目自制时间带，不画复杂队列、红黑树、虚拟截止时间公式。色块不少于 12 mm 宽，缩到正文栏后仍能辨认文字。
- **图前动作/图后判定**：图前提出“界面、网络和相机都想用 CPU 时怎么办”；图后判定为“某一时刻 CPU 只运行选中的任务，OS 会再次选择下一个”。
- **版权与证据标签**：项目自制；图注标 `[教学示意]`，并在图注末尾加“时间块仅表示切换关系，不代表本板固定调度顺序”。
- **替代文本**：`同一条 CPU 时间轴上，界面、网络和相机三个进程分段获得运行机会，顺序与时长由调度器决定。`
- **禁写**：不要写死“每个进程运行 10 ms”；不要把教学时间块称为 Linux 5.10.160 的实测调度结果；不要宣称当前内核一定采用 EEVDF。

### 图 3-4　每个进程看到的内存与实际内存

- **正文作用**：用最少元素解释虚拟内存的两个价值：程序看到自己的地址空间；内核负责把它映射到有限的物理内存并实施隔离/受控共享。
- **画面内容**：左侧两个窄框“进程 A 看到的内存”“进程 B 看到的内存”，每个只画 3 个虚拟页；右侧一个“实际内存”框，画 5 个物理页。箭头表现 A/B 的虚拟页映射到不同物理页；最多保留一个共同指向的浅色页，标“可受控共享”。
- **来源**：Linux 内核虚拟内存概念说明，重点对应虚拟地址翻译、页表映射、隔离和受控共享。
- **制作方式**：项目自制页块图。正文只使用“程序看到的地址”“实际内存”两个通俗标签；“虚拟地址/物理地址/页表”作为图下注释首次贴回正式名称。不要画四级页表、TLB、swap、NUMA 或 OOM。
- **图前动作/图后判定**：图前问“两个程序都以为自己有一块完整内存，会不会互相覆盖”；图后判定为“程序使用的是虚拟地址，内核负责翻译和隔离”。
- **版权与证据标签**：项目自制；图注标 `[教学示意]`。
- **替代文本**：`进程 A 和进程 B 各自看到独立的虚拟页，内核把这些页映射到实际内存中的不同位置，并可控制少量共享。`
- **禁写**：不要保证所有映射都常驻 RAM；不要把示意页数、地址和 RV1106 的真实页表尺寸对应起来；不要引入“内存越大程序越快”的无条件结论。

### 图 3-5　嵌入式 Linux 系统不是一个文件

- **正文作用**：在启动链之前先拆开“系统镜像、Linux、Buildroot、rootfs”这几个容易混淆的词，为第 5 章烧录镜像铺垫。
- **画面内容**：三个并列容器：①“引导程序（常见如 U-Boot）”；②“Linux 内核 + 设备树”；③“根文件系统 rootfs”，其内部只放 `init`、基础命令/库和 boomPI 应用三个例子。容器下方放一条括号：“构建工具可把这些产物组织成可烧录镜像”；不要把 Buildroot 画成板端常驻的一层 OS。

- **图前动作/图后判定**：图前问“烧进板里的镜像是不是只有一个 Linux 文件”；图后要求读者能说出“引导程序、内核/设备树、rootfs 是不同角色，Buildroot 是构建工具”。
- **版权与证据标签**：项目自制；图注标 `[教学示意]`。Buildroot 名称可用纯文字，不使用未经核验的商标素材。

## 6. 版式、可读性与制作验收

### 6.1 统一视觉规则

- 图面背景使用白色或极浅灰；正文黑色；强调色最多三种，同一颜色在全章保持同一含义。
